Problem statement

What a cache stampede actually costs you

A cache stampede — the thundering herd problem — happens when a hot cache key expires and a burst of concurrent requests all miss at once. In the textbook cache-aside pattern (check Redis, fall back to the database, write the result back), every one of those concurrent requests independently makes the same decision: the cache is empty, I need to refill it. None of them know about the others. A key that should cost one database query costs N.

The dangerous part isn't that it fails — it's that it usually doesn't. The database queues the extra load instead of rejecting it, latency creeps up instead of crashing, and the only visible symptom is a bigger infrastructure bill and a p99 graph nobody's watching closely enough. This project exists to make that invisible failure mode visible, measure it honestly, and then fix it with the standard toolkit: distributed locking, request coalescing, TTL jitter, and stale-while-revalidate — each one built, and each one proven against the real stack rather than assumed to work.

Part Two · Milestones 6–9

The fix: four mitigations, composed

Every stampede-prevention technique in the standard toolkit does one job. Composed together in ProductService.GetProduct, they turn "every concurrent miss is a database query" into "at most a handful of database queries, no matter how large the burst."

M6 · Redis distributed lock

internal/cache/lock.go: SETNX acquires a per-key refill lock; a Lua compare-and-delete releases it, so a process can never release a lock it no longer holds. This is the one mitigation that specifically coordinates across API processes — something no in-process technique can do. Proven with two independent API processes sharing the same Redis and PostgreSQL:

two processes, one cold key, simultaneous requests:8080 vs :8081
:8080 cache miss → acquired lock → fetched DB → 200 in 1.3ms (db_fetches: 5→6) :8081 cache miss → lock held elsewhere, waiting→ 200 in 21.1ms (db_fetches: unchanged at 1)

The second process never queried Postgres. It wasn't fast because it got lucky — it waited, on purpose, for the first process's answer.

M7 · Go singleflight

Cross-process coordination doesn't help two goroutines in the same process — that's what golang.org/x/sync/singleflight is for. Concurrent callers for the same key share one in-flight call and its result. Fired 50 genuinely concurrent requests at a never-cached key:

50 concurrent curl requests · cold keybash background jobs
50 requests → 14 detected a cache miss → 1 actual database query all 50 responses: 200 OK, 0.3–4.5ms

M8 · TTL jitter

Coalescing a single key's stampede is only half the story — if every key in the cache was warmed at the same moment (a cold-start, a deploy), they'd all expire in lockstep and stampede together. Redis's own expiry is softTTL + staleTTL ± jitter, so keys desynchronize:

5 products cached simultaneouslyTTL=3s STALE=3s JITTER=0.2
product:1 TTL 7s product:2 TTL 7s product:3 TTL 5s product:4 TTL 5s product:5 TTL 7s

Base expiry (soft + stale) is 6s; with jitter it spreads across 5–7s instead of every key dying on the same clock tick.

M9 · Stale-while-revalidate

A cache entry past its soft TTL but still within the stale window is served immediately — no request ever blocks on a refill — while a background refresh runs, coalesced through the same singleflight group used for hard misses:

request at age 3.5s (past 3s soft TTL)GET /products/5
cache stale hit, serving while revalidating age=3.506s → 200 in 619µs …background refresh completes… TTL immediately after: 6 (fresh window restored, client never waited for it)

Learnings

What building this actually taught

  • Detection and cost are two different numbers. Coalescing doesn't reduce how many requests notice a cold cache — it reduces how many of them are allowed to act on it. cache_misses_total and product_db_fetches_total diverging is the whole point, and both need to be measured, not just one.
  • Counters survive scrape gaps; instantaneous gauges don't. A sub-millisecond burst of 63 concurrent misses was fully captured by a monotonic counter across a 5-second Prometheus scrape interval, while a live connection-pool gauge never caught the spike in-flight — only its lasting footprint (idle connections that stayed elevated). Dashboards prove a stampede happened; they don't always prove what it looked like at the instant it happened.
  • Stampedes fail silently, not loudly. Every load test in this project — naive and mitigated — returned 0% HTTP errors. PostgreSQL's connection pool queues rather than rejects. That's worse for detection, not better: a system that degrades this quietly needs deliberate measurement, because it will never page anyone on its own.
  • Distributed locking only matters once there's more than one process. singleflight alone already collapses a burst to one fetch per process. The lock's entire, provable contribution is cross-process: two processes, one request each, and only one of them touches the database. Test that specific scenario directly, or you can't tell the two mitigations apart.
  • Coalescing trades a little latency for a lot less load. Followers waiting on a shared singleflight result can't return faster than the leader's own database round trip — so a few individual requests were marginally slower under coalescing than an independent (naive) fetch might have been. That's the correct trade: protecting the database is worth a few milliseconds of tail latency.
