A cache stampede — the thundering herd problem — happens when a hot cache key expires and a burst of concurrent requests all miss at once, each independently falling through to the database. None of them know about the others. Every one of them thinks it's the only request that needs to refill the cache. The database gets hit N times for a value that only needed to be fetched once.

It's a well-known failure mode, but it's rarely something engineers get to watch happen with real numbers attached. So this project builds it on purpose: a real Go backend, a real PostgreSQL + Redis cache-aside layer, a real k6 load test, and real Prometheus/Grafana instrumentation — then measures exactly how bad the naive version is before fixing it.

Milestone 1

A foundation that doesn't cut corners

Before any caching logic, the service got the boring parts done properly: env-validated config, structured Zap logging, a pgx connection pool, a go-redis client, request-scoped middleware (request ID, logging, recovery, timeout), Prometheus registration, and /health / /ready endpoints wired to real dependency checks — all behind a strict Handler → Service → Repository → Infrastructure dependency direction.

The graceful shutdown sequence is the kind of thing that's invisible until it isn't:

Milestone 2

Persistence, and making it provably idempotent

A hand-rolled migration runner (built on pgx directly, no framework beyond what the stack already needed) tracks applied versions in a schema_migrations table. Seed data is idempotent by design — safe to re-run in any environment without duplicating rows.

terminalidempotency check
$ make migrate-up migration applied {"version": "0001_create_products_table"} $ make migrate-up # run again (nothing to apply) $ make db-seed INSERT 0 5 $ make db-seed # run again INSERT 0 0
Milestone 3

The naive cache-aside pattern — and why it's naive

The textbook pattern: check Redis, fall back to PostgreSQL on a miss, write the result back to Redis with a TTL, return. It works. A single request against a cold key measurably proves the cache is doing its job:

same endpoint, back to backGET /products/1
cache miss {"product_id": 1} → 200 in 3.19ms (Redis GET, then Postgres, then Redis SET) cache hit {"product_id": 1} → 200 in 340µs (Redis GET only)

That's the whole point of the pattern — and also, silently, the whole setup for what comes next. Nothing here coordinates between concurrent requests. Every one of them makes its own independent decision about whether to trust the cache.

Milestone 4 · the centerpiece

Reproducing the stampede, on purpose, with a stopwatch

A k6 script primes the cache with one request, waits for the TTL to expire, then fires a burst of virtual users at the same key simultaneously — the exact condition a real production hot-key expiry creates. Run twice, against the real stack, at two burst sizes:

k6 stampede runsload/stampede.js
burst sizeconcurrent misseswindowhttp errors
50 virtual users13 (12 within 17ms)17ms0%
200 virtual users19 (18 within 1ms)1ms0%
The count didn't scale linearly with burst size — because the naive implementation is fast enough that some requests land after the first miss has already repopulated the cache. But a double-digit number of simultaneous, redundant database queries from a single expired key is the stampede, measured, not simulated.
Zero request failures, in both runs. pgxpool queues rather than rejects when a burst exceeds the connection pool. Nothing crashed. Nothing errored. It just got slower and did more redundant work — which is precisely why stampedes go unnoticed in production until the database bill or the p99 graph says otherwise.
Milestone 5

Instrumenting it well enough to watch it happen

Prometheus scrapes the API every 5 seconds; a provisioned Grafana dashboard (no manual setup — datasource and panels ship as code) tracks request rate, latency percentiles, cache hit ratio, hits vs. misses, and PostgreSQL pool connections. Two panels below, captured live from this exact session:

Request rate and p50/p95/p99 latency both spike during the stampede burst, then flatten — visible within 15 minutes of real traffic, no synthetic data.
Steady state settles at a 95% hit ratio. The pool panel on the right is the interesting one — see below.
Counters survive scrape gaps. Gauges of instantaneous state don't. A 500-VU burst produced 63 concurrent cache misses in under a millisecond — far faster than Prometheus's 5-second scrape interval, and faster than manual polling at ~7ms could resolve. The cache_misses_total counter still recorded all 63 correctly, because counters accumulate between scrapes. The postgres_pool_acquired_conns gauge, an instantaneous snapshot, never caught the spike in-flight — but its lasting footprint did show up: idle connections climbed from 0 to the pool's configured max of 10 and stayed there. The contention was real. It was just faster than any periodic scrape could witness directly.

That distinction matters more than it sounds: it's the difference between a dashboard that proves a stampede happened and one that only proves the server survived it.

5 / 10 milestones

We're halfway. Nothing is fixed yet.

A production-shaped foundation, real persistence, the textbook cache-aside pattern, a measured reproduction of its worst failure mode, and instrumentation good enough to watch that failure happen in real time. The naive implementation is still naive — on purpose. Part 2 is the fix:

  • 06 Redis distributed lock — only one request refills the cache
  • 07 Go singleflight — in-process request coalescing
  • 08 TTL jitter — spread expirations so keys don't die in lockstep
  • 09 Stale-while-revalidate — serve stale, refresh in the background
  • 10 Benchmark comparison — every mitigation, measured against the baseline above
